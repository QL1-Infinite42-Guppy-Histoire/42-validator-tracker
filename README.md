## 何が表示されるか

- ライブフィード：時刻（JST）／区分バッジ（本人・関連・中核）／アドレス（末尾4文字表示、タップで公式エクスプローラー）／分類（送金・受取／買い／売り／LP追加／LP解除／委任・委任解除・委任先変更／報酬請求（委任報酬）・バリデーター報酬請求（コミッション）・報酬請求（FISH配布）ほか／NFTミント／Fluke参加・確定／使用許可（approve）など、判別できた範囲の具体名。判別できないものは「未分類の操作（メソッド／宛先）」と表示）／銘柄と金額／相手／Txリンク。Cosmos側の動きには「Cosmos側」バッジが付き、Txリンクは自作の Cosmos スキャナー（https://ql1-infinite42-guppy-histoire.github.io/42-cosmos-scan/ の Tx ビュー）に飛びます（公式の Blockscout は Cosmos Tx を表示しないため）
- **ブリッジ出金（USDT・外部へ）**（バリデーター本人・直接関連が **USDT** をブリッジ経由で42チェーンから外部チェーンへ送り出した動き）は、専用の緑色の欄で光って表示されます（「注目」には入れません）。**v0.2.3 で対象を USDT のみに限定**しました：USDT以外の銘柄のブリッジ送信は「ブリッジ送信（USDT以外）」として通常の動きに記録され、緑色の欄には入りません。入金（受取）は通常の送金・受取で、特別表示はしません
- **完全英語版**：同じ feed.json を使う英語ページ `en.html` を併設（見出し・定義文・イベント文すべて英語。イベント文は保存済みの日本語要約を使わず、構造化フィールドから英語で組み立てます）。各ページの冒頭に相互リンク（English version／日本語版）があります
- **見出しは「動いた本人」だけ**を表示します（v0.2.0で修正）。関係するバリデーターは別の行に「関係バリデーター：○○ ほか△名」と上限付きで分け、3名以上のバリデーターと取引するアドレスには「共有の相手先」バッジ＋説明を付けます（複数のバリデーター名を見出しに並べて、共同で動いたように見える表示はしません）
- 絞り込み：バリデーター別・種類別・銘柄別
- バリデーター一覧（23名、それぞれの直接関連アドレス数つき。Cosmos側の bech32 アドレス `infinite1…` も feed.json に併記）
- **「⚠ インサイダー」欄（最上部・紫色の警告風デザイン）**：**バリデーターX本人とXの直接関連アドレスによる、[42] と DONT（PANIC）の動きだけ**を表示します。判定は collector が `isInsider` フラグとして付けます（役務は watchlist の確認済み直接関係のみ。ペア・ルーター等の仕組み系アドレスと、別バリデーターである Xenia は対象外）。表示は新しい順に直近100件＋総件数表示で、記録は全件残ります
- **「🎯 スナイプ速報」欄**：スナイプの定義は **ペアが作られてから3時間以内に、バリデーター本人または直接関連ウォレットが、そのペアで買った（買い）動き**（v0.2.4 で変更：**LP追加はスナイプに含みません**）。ペアの作成時刻は Blockscout の作成Tx（creation_transaction_hash）から取得して `pairs-creation.json` にキャッシュします。当てはまる動きが無い期間は「直近のスナイプは検出されていません」と定義ごと表示します
- 「注目」欄（サイト内アラート）：ルールは明示しています —
  ① バリデーター本人の売買、② 1,000 [42] 以上の移動。条件は `collector.mjs` の `NOTABLE_42_THRESHOLD` とサイト上の表記が正です
- ステータス行：最終処理ブロック番号（EVM側／Cosmos側）と更新時刻（鮮度が誰にでも分かります）

## 仕組み

```
42 Chain (EVM RPC)                        42 Chain (CometBFT RPC / Cosmos側)
   │  新ブロックを確認                        │  対象メッセージ種別ごとに tx_search
   ▼                                          ▼
ブロック＋レシート → ログ復号              Tx本体を protobuf 復号してメッセージ単位で分類
（Transfer / V2 Swap・Mint・Burn）        （MsgSend / 委任・解除・変更 / 報酬・手数料）
   │                                          │  ※ MsgEthereumTx はEVM側と重なるので対象外
   └──────────────┬───────────────────────────┘
                  ▼
監視アドレスに絡む動きだけを events.jsonl に追記
（IDで重複排除、state.json に EVM / Cosmos 両方のチェックポイント）
                  ▼
feed.json（最新500件）を再生成 → 静的サイト index.html が30秒ごとに読み直し
```

Cosmos側の初回だけは全履歴を一括取り込みします（このチェーンの Cosmos ネイティブ取引は全期間でも約800件と少ないため）。以後はチェックポイント以降の高さだけを tx_search で引くので、5分間隔の Actions 実行に十分収まります。Cosmos の高さと EVM のブロック番号はこのチェーンでは一致しますが、チェックポイントは安全のため別々に保持します（`state.json` の `lastProcessedCosmosBlock`）。

### 分類ルール（collector.mjs）

- **送金／受取**：ERC-20 Transfer とネイティブ[42]の移動。**金額の下限は一切ありません**（小さな送金も全て記録 — ユーザーの standing rule）。両側が監視対象なら、バリデーター本人を主役にします
- **買い／売り**：V2 Swap を「本人の資産の変換」として記録（人物→人物の線にはしません）。[42]/USDT 側を基準通貨として、非基準通貨を受け取れば「買い」、払えば「売り」。USDT→[42]は[42]の買い、[42]→USDTは[42]の売り。価格はスワップ量そのものから計算します
- **LP追加／LP解除**：Mint／Burn イベント。実行者は Tx送信者とLPトークンの発行・焼却先から特定します
- **その他の操作**：上記に当てはまらない、監視アドレスからのコントラクト実行。ただし同一アドレス・宛先・メソッドの繰り返しは約360ブロック（約30分）に1回まで記録します（キーパー的な関連アドレス 0xbfc5…4f29 の同一コール連打でフィードが埋まるのを防ぐため。送金・売買・LPは一切抑制しません）
- Swap／LP を含む Tx の内部 Transfer は、その変換の一部なので二重に記録しません
- **スナイプ判定**：買いのイベントに、ペア作成時刻（`pairs-creation.json`）から計算した「作成後の経過秒数」を付け、3時間以内なら `isSnipe=true`（v0.2.4 から買いのみ。LP追加には経過秒数は付きますがスナイプにはなりません）。保存済みイベントにも同じ判定を後付けします（遡及フラグ）。作成時刻が解決できないペアは判定しません（推測で埋めません）
- **インサイダー判定（v0.2.4、表示範囲は v0.2.5 で絞り込み）**：イベントの actor が「バリデーターX本人」または「Xの直接関連アドレス（related 区分・ペア/中核を除く）」で、かつ動いた銘柄に [42]（ネイティブマーカー 0xeeee…）または DONT（PANICコントラクト 0xfaa842…）が含まれる場合に `isInsider=true`。feed 生成ではスナイプ／ブリッジ出金と同様に常時含有されます

### Cosmos側の分類ルール（collector.mjs、v0.2.0）

- 取得は CometBFT の `tx_search`（メッセージ種別ごと、高さ範囲つき、全ページ走査）。Tx本体を最小 protobuf デコーダーで復号してメッセージ単位で見るので、**手数料レッグは構造的に混入しません**（手数料は AuthInfo 側にあり、メッセージには現れません）
- **送金（bank MsgSend）**：`drop` は [42]（18桁）として表示。それ以外の denom はそのまま表示し対象外扱い。**金額の下限は一切ありません**（Xenia の 2 [42] のような小額送金が典型例）
- **委任／委任解除／委任先変更**（staking MsgDelegate / MsgUndelegate / MsgBeginRedelegate）：宛先バリデーターは valoper アドレスを復号してアカウントと同一の20バイトに直し、名前で表示します
- **報酬受取／手数料報酬**（distribution MsgWithdrawDelegatorReward / MsgWithdrawValidatorCommission）：金額は Tx の実行結果イベント（withdraw_rewards / withdraw_commission）から取得します
- **MsgEthereumTx は完全に対象外**です（EVM側で既に記録されるため、二重計上を防ぎます）
- Cosmos アドレス（bech32 `infinite1…` / `infinitevaloper1…`）は自前の bech32 実装で16進アドレスに変換し、EVM側と同一の監視リストで照合します

## ローカルでの動かし方

```bash
node build-watchlist.mjs          # watchlist.json / registries.json を生成（初回のみ）
node collector.mjs --backfill 300 # 直近300ブロックを処理して feed.json を作る
node collector.mjs --once         # チェックポイントから先端まで1回処理（EVM＋Cosmos）
node collector.mjs --cosmos-backfill 20000  # Cosmos側だけ直近N高さを再走査
node collector.mjs                # 常駐モード（約10秒間隔、POLL_MS で変更可）
node server.mjs                   # http://localhost:8787/ でサイト表示
node test-decoder.mjs             # 既知の過去フロー2件（スワップ／送金）で復号を照合
node test-render.mjs              # v0.2.0 見出し表示の回帰テスト（共有の相手先の誤認防止）＋WS4/WS5表示確認
node test-en.mjs                  # v0.2.3 英語版の回帰テスト（全イベント種別の英語レンダリング＋日本語が混ざらないこと＋ブリッジ出金=USDTのみ確認）
node test-ws4.mjs                 # WS4/WS4b/WS5 分類テスト（実在のGuide settle TxフィクスチャでNFTミント検出を照合）
node test-cosmos.mjs              # Cosmos復号の照合（bech32往復／MsgSendと msg_index レッグの一致）
```

ファイル構成：`collector.mjs`（収集・分類、EVM＋Cosmos）／`build-watchlist.mjs`（監視リスト生成）／`watchlist.json`・`registries.json`（生成物）／`events.jsonl`（全イベント追記、`chain` フィールド付き）／`feed.json`（最新500件）／`state.json`（EVM／Cosmos チェックポイント）／`pairs-cache.json`（新規ペアの token0/token1 キャッシュ）／`pairs-creation.json`（ペア作成ブロック・時刻のキャッシュ）／`index.html`（サイト本体、外部CDNなし）／`en.html`（完全英語版、同じ feed.json を使用）／`server.mjs`（ローカル確認用）／`test-decoder.mjs`・`test-render.mjs`・`test-cosmos.mjs`・`test-ws4.mjs`・`test-en.mjs`（検証）

RPCの注意：42 Chain の RPC はブラウザ風 User-Agent を付けないと接続を切ることがあります（実測済み）。`collector.mjs` は最初から付けており、ホスト2系統（infinitepanda → mschihuahua）の切替＋リトライも入っています。ブロック間隔は実測で約5.4秒と安定しています。

## ホスティング案（維持費0円が前提）

### 第一候補：GitHub Actions ＋ GitHub Pages（同梱テンプレートあり）

公開リポジトリなら GitHub Actions は無料・無制限です。`.github/workflows/collect.yml`（同梱・運用中）が次を行います：

1. 5分間隔（Actions の cron 最短間隔。混雑時は遅延あり）に起動
2. `node collector.mjs --once` でチェックポイント以降のブロック（約55ブロック分）を処理
3. 更新された `feed.json`／`events.jsonl`／`state.json` をリポジトリにコミットして戻す
4. サイト配信は GitHub Pages（main ブランチ直下を有効化するだけ、無料）

遅延してもチェックポイント方式なので取りこぼしはなく、次回にまとめて追いつきます。鮮度はサイトのステータス行で常に確認できます。
注意：スケジュール実行はデフォルトブランチでのみ有効で、リポジトリが60日間無活動だと GitHub が自動で止める場合があります（このワークフローのデータコミット自体が活動になります）。監視リストの再生成は Actions 内では行いません（生成元データはローカルの調査フォルダにあるため、ローカルで生成してコミットします）。

### 第二候補：Cloudflare Workers Cron ＋ Pages

無料枠は Cron 1分間隔・リクエスト100,000回/日と余裕がありますが、Cron の CPU 時間制限が厳しく、数百ブロック分のレシート復号を1回の実行に詰める今の作りとは相性が要検証です（実行を小分けにする改修が前提）。Pages への配信自体は無料で問題ありません。

### 任意（有料）：小さな VPS

常駐モード（約10秒間隔ポーリング）をそのまま動かせて最もリアルタイムに近いですが、月額がかかるため **0円前提では採りません**。必要になった場合の選択肢としてだけ挙げておきます。

## v0.2.0 の範囲と限界（正直な表記）

- EVM側＋Cosmos側（送金・委任・委任解除・委任先変更・報酬請求）が対象です。Cosmos側のその他のメッセージ種別（ガバナンス投票など）は未対応です
- 操作の詳細分類は「宛先コントラクト＋メソッドセレクタ」の明示的な対応表（検証済みABIと過去調査が出どころ）だけで行い、推測で名前を作りません。対応表に無い呼び出しは「未分類の操作（メソッド 0x…／宛先 …末尾4文字）」と表示します。移行時点の実績：旧「その他の操作」26件のうち25件が具体分類に移り、未分類は1件（メソッド 0x98869d1f／宛先は名称不明のプロキシ）だけが残りました
- 報酬請求の実績（移行時点）：Cosmos側の委任報酬請求 422件・コミッション請求 302件、EVM側の FISH配布請求 6件。EVM側のステーキング報酬請求（プリコンパイル 0x0801 の claimRewards）と Starlight報酬請求は仕組みだけ入っていて実績はまだ0件です
- ブリッジで外部へ送信の検出（ブリッジ系コントラクト宛の送金／ブリッジ送信メソッド）も仕組みは入っていますが、保存済みデータ内の実績はまだ0件です（表示確認はフィクスチャで実施）→ **v0.2.2 で掘り起こし分26件（21tx）を追加し、実績ありになりました**
- スナイプ速報は「ペア作成時刻が解決できた買い」だけが判定対象です（v0.2.4 から LP追加は対象外）。作成時刻の分からないペアは判定しません

## v0.2.2 掘り起こし（バックフィル）について

- リアルタイム収集の開始前（2026-11-05以前）の履歴は、42-flowmap の全Txフロー索引（ブロック17,619〜）から候補を抽出し、実際のTx/レシートをRPCで再取得して collector 自身の分類器で再構築しました。各イベントには `backfill: true` フラグが付きます（表示は通常イベントと同じ）
- スナイプ 85件（買い52＋LP追加33／本人5・関連80）、ブリッジ出金 26件（21tx分／本人2・関連24。うち5件は transferRemote 実行時のネイティブ手数料分で、ライブ収集でも同じ形で記録されるもの）
- feed.json は「最新500件＋全スナイプ＋全ブリッジ出金」の合算（重複除き）になり、掘り起こし分が500件枠から落ちることはありません
- 先行調査（validator-sniping.json）との定義差：あちらは「最初のスワップから1時間・買いのみ・推定リンク含む」、こちらはサイト定義どおり「ペア作成から3時間・買い＋LP追加・本人＋直接関連のみ（推定なし）」。先行調査の本人＋直接関連34件は全件こちらにも含まれます
- **推定リンクは含みません**（プール経由などの推定は Phase 3。本人→直接関連の確認済みデータのみ）
- X bot などの外部アラートは行いません（サイト内「注目」だけ）
- バリデーター集合は 2026-10-31 のスナップショットが元です。新規バリデーターの自動取り込みは今後の課題です
- 未知のペアで Swap が起きた場合、その場で token0/token1 を問い合わせてキャッシュします。取得できなかった Swap は記録されません（次回以降の課題）
- 価格はプールのスワップ量からの計算値です。流動性の薄いプールでは実勢とずれることがあります
