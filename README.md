- **「👤 新しい顔ぶれ」欄（v0.4.0）**：監視アドレスが全記録の中で初めてやり取りした相手の出現記録です。新しく現れた相手は、その場で関連アドレス（確定）として watchlist に**自動追加**されます（仕組み系・ペア・トークンのコントラクトと、推定アドレスの相手は追加しません）。追加されたアドレスには経由（via）と深さ（depth）が記録されます

## 仕組み

```
42 Chain (EVM RPC)                        42 Chain (CometBFT RPC / Cosmos側)
   │  新ブロックを確認                        │  対象メッセージ種別ごとに tx_search
   ▼                                          ▼
ブロック＋レシート → ログ復号              Tx本体を protobuf 復号してメッセージ単位で分類
（Transfer / V2 Swap・Mint・Burn）        （MsgSend / 委任・解除・変更 / 報酬・手数料）
   │                                          │  ※ MsgEthereumTx はEVM側と重なるので対象外
   └──────────────┬───────────────────────────┘
                  ▼
監視アドレスに絡む動きだけを events.jsonl に追記
（IDで重複排除、state.json に EVM / Cosmos 両方のチェックポイント）
                  ▼
feed.json（最新500件）を再生成 → 静的サイト index.html が30秒ごとに読み直し
```

Cosmos側の初回だけは全履歴を一括取り込みします（このチェーンの Cosmos ネイティブ取引は全期間でも約800件と少ないため）。以後はチェックポイント以降の高さだけを tx_search で引くので、5分間隔の Actions 実行に十分収まります。Cosmos の高さと EVM のブロック番号はこのチェーンでは一致しますが、チェックポイントは安全のため別々に保持します（`state.json` の `lastProcessedCosmosBlock`）。

### 分類ルール（collector.mjs）

- **送金／受取**：ERC-20 Transfer とネイティブ[42]の移動。**金額の下限は一切ありません**（小さな送金も全て記録 — ユーザーの standing rule）。両側が監視対象なら、バリデーター本人を主役にします
- **買い／売り**：V2 Swap を「本人の資産の変換」として記録（人物→人物の線にはしません）。[42]/USDT 側を基準通貨として、非基準通貨を受け取れば「買い」、払えば「売り」。USDT→[42]は[42]の買い、[42]→USDTは[42]の売り。価格はスワップ量そのものから計算します
- **LP追加／LP解除**：Mint／Burn イベント。実行者は Tx送信者とLPトークンの発行・焼却先から特定します
- **その他の操作**：上記に当てはまらない、監視アドレスからのコントラクト実行。ただし同一アドレス・宛先・メソッドの繰り返しは約360ブロック（約30分）に1回まで記録します（キーパー的な関連アドレス 0xbfc5…4f29 の同一コール連打でフィードが埋まるのを防ぐため。送金・売買・LPは一切抑制しません）
- Swap／LP を含む Tx の内部 Transfer は、その変換の一部なので二重に記録しません
- **スナイプ判定**：買いのイベントに、ペア作成時刻（`pairs-creation.json`）から計算した「作成後の経過秒数」を付け、3時間以内なら `isSnipe=true`（v0.2.4 から買いのみ。LP追加には経過秒数は付きますがスナイプにはなりません）。保存済みイベントにも同じ判定を後付けします（遡及フラグ）。作成時刻が解決できないペアは判定しません（推測で埋めません）
- **インサイダー判定（v0.2.4、表示範囲は v0.2.5 で絞り込み）**：イベントの actor が「バリデーターX本人」または「Xの直接関連アドレス（related 区分・ペア/中核を除く）」で、かつ動いた銘柄に [42]（ネイティブマーカー 0xeeee…）または DONT（PANICコントラクト 0xfaa842…）が含まれる場合に `isInsider=true`。feed 生成ではスナイプ／ブリッジ出金と同様に常時含有されます
- **推定区分のガード（v0.3.0）**：推定アドレスのイベントには `estimateBasis`（方法・根拠文・関係バリデーター）を付けますが、`enrichEvent` の最終段で **スナイプ／インサイダーのフラグと、ブリッジ出金の種別・マーカーを必ず取り除きます**（ブリッジ送信は「ブリッジ送信（USDT以外）」と同じ通常種別に降格）。feed への常時含有（ピン留め）もされません。「最新の動き」の最新500件の範囲に入った分だけが表示されます

### Cosmos側の分類ルール（collector.mjs、v0.2.0）

- 取得は CometBFT の `tx_search`（メッセージ種別ごと、高さ範囲つき、全ページ走査）。Tx本体を最小 protobuf デコーダーで復号してメッセージ単位で見るので、**手数料レッグは構造的に混入しません**（手数料は AuthInfo 側にあり、メッセージには現れません）
- **送金（bank MsgSend）**：`drop` は [42]（18桁）として表示。それ以外の denom はそのまま表示し対象外扱い。**金額の下限は一切ありません**（Xenia の 2 [42] のような小額送金が典型例）
- **委任／委任解除／委任先変更**（staking MsgDelegate / MsgUndelegate / MsgBeginRedelegate）：宛先バリデーターは valoper アドレスを復号してアカウントと同一の20バイトに直し、名前で表示します
- **報酬受取／手数料報酬**（distribution MsgWithdrawDelegatorReward / MsgWithdrawValidatorCommission）：金額は Tx の実行結果イベント（withdraw_rewards / withdraw_commission）から取得します
- **MsgEthereumTx は完全に対象外**です（EVM側で既に記録されるため、二重計上を防ぎます）
- Cosmos アドレス（bech32 `infinite1…` / `infinitevaloper1…`）は自前の bech32 実装で16進アドレスに変換し、EVM側と同一の監視リストで照合します

## ホスティング案（維持費0円が前提）

### 第一候補：GitHub Actions ＋ GitHub Pages（同梱テンプレートあり）

公開リポジトリなら GitHub Actions は無料・無制限です。`.github/workflows/collect.yml`（同梱・運用中）が次を行います：

1. 5分間隔（Actions の cron 最短間隔。混雑時は遅延あり）に起動
2. `node collector.mjs --once` でチェックポイント以降のブロック（約55ブロック分）を処理
3. 更新された `feed.json`／`events.jsonl`／`state.json` をリポジトリにコミットして戻す
4. サイト配信は GitHub Pages（main ブランチ直下を有効化するだけ、無料）

遅延してもチェックポイント方式なので取りこぼしはなく、次回にまとめて追いつきます。鮮度はサイトのステータス行で常に確認できます。
注意：スケジュール実行はデフォルトブランチでのみ有効で、リポジトリが60日間無活動だと GitHub が自動で止める場合があります（このワークフローのデータコミット自体が活動になります）。監視リストの再生成（build-watchlist / build-estimates）は Actions 内では行いません（生成元データはローカルの調査フォルダにあるため、ローカルで生成してコミットします）。ただし v0.3.0 のバリデーター名簿の自動更新はチェーンの RPC だけで完結するため Actions 内でも動き、変更があれば `watchlist.json` もデータコミットに含まれます。

### 第二候補：Cloudflare Workers Cron ＋ Pages

無料枠は Cron 1分間隔・リクエスト100,000回/日と余裕がありますが、Cron の CPU 時間制限が厳しく、数百ブロック分のレシート復号を1回の実行に詰める今の作りとは相性が要検証です（実行を小分けにする改修が前提）。Pages への配信自体は無料で問題ありません。

### 任意（有料）：小さな VPS

常駐モード（約10秒間隔ポーリング）をそのまま動かせて最もリアルタイムに近いですが、月額がかかるため **0円前提では採りません**。必要になった場合の選択肢としてだけ挙げておきます。
